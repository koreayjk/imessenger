# 배포하기 — TCS 를 실제로 바꾸는 길

TCS 는 **네 군데**가 따로 움직입니다. 고친 자리에 따라 올리는 곳이 다릅니다.
한 군데만 올리고 "다 했다" 고 하면, 멘트는 달렸는데 화면은 안 바뀐 상태가 됩니다.

| 고친 것 | 올리는 곳 | 어떻게 |
|---|---|---|
| `index.html` 등 화면 파일 | 웹 (GitHub Pages) | **`main` 에 푸시하면 자동** |
| `supabase/functions/*` | Supabase Edge Function | 따로 올려야 함 |
| `db/*.sql` | Supabase 데이터베이스 | 따로 돌려야 함 |
| 아이폰 · 맥 앱 | App Store · dmg | 따로 빌드 (아래 다른 문서) |

---

## ① 화면 (`index.html`) — `main` 에 푸시하면 끝

`.github/workflows/deploy-pages.yml` 이 **`main` 푸시마다** GitHub Pages 로 올립니다.
따로 업로드할 것이 없습니다.

```bash
# 작업 브랜치에서 일하고
git push -u origin <작업브랜치>

# main 으로 넘긴다 (빨리감기만 — main 에만 있는 커밋이 없을 때)
git push origin <작업브랜치>:main
```

넘기기 전에 **빨리감기가 되는지** 먼저 봅니다. 아래가 비어 있어야 안전합니다
(비어 있지 않으면 main 에 내가 모르는 커밋이 있다는 뜻입니다 — 먼저 합쳐야 합니다).

```bash
git fetch origin main
git log --oneline origin/main --not <작업브랜치>
```

### 올라갔는지 확인하는 법

푸시하고 **20~30초쯤** 걸립니다. 두 가지를 봅니다.

1. 워크플로가 성공했는지 — https://github.com/koreayjk/imessenger/actions
   `Deploy site to GitHub Pages` 가 초록색이면 됩니다.
   (`pages build and deployment` 라는 것도 같이 돌아갑니다. 깃허브가 자동으로
   붙이는 것이라 둘 다 초록이어야 합니다.)

2. 실제 사이트 파일이 저장소 파일과 같은지 — 이게 가장 확실합니다.

```bash
curl -sS -o /tmp/live.html https://koreayjk.github.io/imessenger/index.html
cmp -s index.html /tmp/live.html && echo "✅ 똑같다" || echo "❌ 아직 옛 파일"
```

### 사람들이 새 화면을 보는 때

`sw.js` 는 **화면 파일을 캐시하지 않습니다**(일부러 그렇게 두었습니다 —
2MB 짜리 `index.html` 을 캐시하면 고쳐도 옛 화면이 남습니다).
그래서 **새로고침하면 바로** 새 화면이 됩니다. 앱으로 설치해 쓰는 분도
앱을 닫았다 열면 됩니다.

> ⚠️ **아이폰 앱(App Store 로 받은 것)은 다릅니다.** 화면이 앱 안에 들어가
> 있어서, 웹을 올려도 안 바뀝니다. `npm run sync` 로 `www/` 를 다시 만들고
> App Store 에 새 버전을 올려야 합니다 (`docs/앱스토어_출시절차.md`).

## ② 서버 함수 (Supabase Edge Function)

`supabase/functions/<이름>/index.ts` 를 고쳤으면 **그 함수를 따로 올려야**
합니다. git 푸시로는 안 올라갑니다.

Supabase 대시보드 → Edge Functions → 해당 함수에서 올립니다.
CLI 로도 되지만 **접속 토큰(`SUPABASE_ACCESS_TOKEN`)이 있어야** 합니다
(대시보드 → Account → Access Tokens. 이 토큰은 git 에 올리지 마세요).

```bash
export SUPABASE_ACCESS_TOKEN=<본인 토큰>
npx supabase functions deploy <이름> --project-ref bbfvnmlrdtzmcwfadjqw
```

올린 뒤에는 **올라간 내용이 저장소 파일과 같은지 확인**하세요.
손으로 옮기다 주석이 틀어진 일이 있었습니다.
대시보드에서 올라간 소스를 열어 저장소 파일과 맞춰 보면 됩니다.

지금 **올라가 있는** 함수 (12개):
`gcal-sync` · `drive-list` · `push-notify` · `store` ·
`admin-create-student` · `analyze-reading` · `analyze-mockexam` ·
`draft-assessment` · `books-search` · `parent-verify` ·
`delete-account` · `turn-credentials`

> `supabase/functions/imnote/` 는 저장소에만 있고 **올라가 있지 않습니다**
> (2026-11-10 확인). 쓸 생각이면 올려야 하고, 안 쓸 거면 지우는 게 낫습니다 —
> 지금처럼 두면 "고쳤는데 왜 안 되지" 하고 헤매게 됩니다.

## ③ 데이터베이스 (`db/*.sql`)

`db/` 에 새 `*_DB설치.sql` 이 생겼으면 **한 번 돌려야** 합니다.
Supabase 대시보드 → SQL Editor 에 내용을 붙여넣고 실행합니다.

- 파일 머리에 무엇을 왜 고치는지 적어 두었습니다. 읽고 돌리세요.
- 두 번 돌려도 터지지 않게 써 두었습니다 (`if not exists` 등).
- **돌리지 않으면** 화면은 새것인데 기능이 안 먹습니다. 그럴 때 TCS 는
  "db/○○.sql 을 실행해주세요" 라고 알려 줍니다 — 그 말이 보이면 ③이 안 된 것입니다.

## ④ 순서 — 서버·DB 를 먼저

같은 기능에서 여러 군데를 고쳤으면 이 순서가 안전합니다.

```
③ DB  →  ② 서버 함수  →  ① 화면(main 푸시)
```

DB 칸이 없는데 화면이 먼저 올라가면, 쓰는 사람이 눌렀을 때 실패합니다.
거꾸로 DB·서버가 먼저 올라가 있으면, 새 칸은 아무도 안 쓰는 채로 가만히
있다가 화면이 올라오는 순간 켜집니다.

## ⑤ 다 끝내고 — 개선창 멘트

개선창(`improvements`) 글에서 올라온 요청이면, **①까지 올라간 뒤에**
완료 멘트를 답니다. 먼저 달면 보러 오신 분이 못 찾습니다.

- 관리자 답변으로 달고(`is_admin = true`), 상태를 `done` 으로 바꿉니다.
- 어디로 들어가면 되는지(예: "학사 → 시간표 → 📔 주간 기록") 적어 주세요.
  "고쳤습니다" 만 적으면 어디를 봐야 할지 모릅니다.

## 되돌리기

웹은 `main` 을 뒤로 돌리고 다시 푸시하면 됩니다.

```bash
git push origin <되돌릴커밋>:main --force-with-lease
```

DB 는 되돌리는 파일이 따로 있는 것만 되돌아갑니다
(예: `db/트렁케이트_되돌리기.sql`). 없으면 반대 SQL 을 새로 써야 하니,
지우거나 덮어쓰는 설치는 돌리기 전에 꼭 읽어 보세요.
